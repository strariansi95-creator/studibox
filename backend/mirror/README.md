# RU-зеркало Studibox (Yandex Cloud Functions)

Зачем: у части операторов РФ (замечено на Билайне) нестабильно
блокируется/режется трафик к Supabase/Cloudflare. Эта функция стоит между
приложением и Supabase, физически в российской инфраструктуре — операторы
РФ такую не блокируют. Сама Supabase-функция `schedule-api`, импорт XLSX и
парсер расписания не трогаются вообще.

Файл функции: `index.js` в этой папке. Без внешних npm-зависимостей —
только встроенный модуль `https`.

## 1. Создать функцию

1. Зайдите в [Yandex Cloud Console](https://console.yandex.cloud/) →
   **Cloud Functions** → «Создать функцию».
2. Среда выполнения: **Node.js 18** (или новее).
3. Загрузите `index.js` как есть (через веб-редактор — просто вставьте
   содержимое файла, отдельно архивировать не нужно).
4. Точка входа (entrypoint): `index.handler`.
5. Таймаут: 15 секунд. Память: 128 МБ — этого достаточно, функция только
   пересылает JSON.

## 2. Переменные окружения

В настройках функции → «Переменные окружения»:

| Имя | Значение |
|---|---|
| `SUPABASE_HOST` | `gdjpevzioenbeyammukm.supabase.co` |

`ALLOWED_PREFIX` и `CACHE_TTL_MS` можно не задавать — у них разумные
значения по умолчанию (см. комментарии в `index.js`).

## 3. Публичный HTTP-триггер

1. На странице функции → вкладка **«Триггеры»** → «Создать триггер».
2. Тип: **HTTP**. Авторизация: **не требуется** (публичный доступ) — сама
   функция ничего чувствительного не отдаёт, а `ALLOWED_PREFIX` не даёт
   использовать её как открытый прокси на произвольные хосты.
3. После создания скопируйте вызываемый адрес функции — он выглядит так:
   `https://functions.yandexcloud.net/<ID функции>`.

## 4. Проверка

```bash
curl "https://functions.yandexcloud.net/<ID функции>?p=/functions/v1/schedule-api/api/health"
```

Должен вернуться тот же JSON, что отдаёт сама Supabase-функция по
`/api/health`. Проверьте так же `api/groups` и `api/schedule/<ваша группа>`.

## 5. Подключить к приложению

В `android/app/build.gradle.kts` найдите `MIRROR_BASE_URL` и замените
плейсхолдер на реальный адрес функции **с завершающим слэшем**:

```kotlin
buildConfigField(
    "String",
    "MIRROR_BASE_URL",
    "\"https://functions.yandexcloud.net/<ID функции>/\""
)
```

Больше ничего менять не нужно — `NetworkModule.kt` сам сначала пробует
зеркало, а если оно недоступно (например, функцию ещё не задеплоили или
временно упала) — идёт напрямую на Supabase, как раньше. Если
`MIRROR_BASE_URL` оставить плейсхолдером, приложение просто продолжит
работать по-старому, напрямую.

## Ограничения и что можно улучшить позже

- Кеш в функции — только в памяти «тёплого» инстанса Yandex Cloud
  Functions (несколько минут между холодными стартами). Это снижает
  нагрузку на Supabase и ускоряет повторные запросы, но не гарантирует
  идеальную свежесть данных — для расписания, которое обновляется раз в
  несколько часов, это не критично.
- Если хочется вообще не зависеть от живого запроса к Supabase в момент
  обращения студента — следующий шаг: добавить в `backend/sql/cron.sql`
  дополнительный шаг, который после каждого импорта XLSX кладёт снимки
  `api/groups` и `api/schedule/<группа>` в Yandex Object Storage
  (S3-совместимое, тоже RU-хостинг) как статические файлы. Это уберёт
  единую точку отказа «Supabase не ответил», но требует отдельной
  реализации и подписи S3-запросов — сознательно не делал этого сейчас,
  чтобы не трогать рабочий импорт без крайней необходимости.
- Домен `functions.yandexcloud.net` тоже можно спрятать за собственным
  доменом через Yandex API Gateway + свой DNS, если понадобится вообще не
  светить `yandexcloud.net` — но пока не блокируется, лишний шаг не нужен.
